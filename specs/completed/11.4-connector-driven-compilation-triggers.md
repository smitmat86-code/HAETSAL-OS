# Session 11.4 - Connector-Driven Compilation Triggers

Status: Active
Owner: Codex
Date: 2026-04-22

## Why This Session Exists

Session 11.0 established the compiled-synthesis foundation.

Session 11.1 refined the compiled object model.

Session 11.2 built the first compiler.

Session 11.3 made the Chief of Staff prefer compiled outputs.

The next gap is freshness:

- the brain should update its compiled understanding when source truth changes

Without that, plugging new inputs into HAETSAL will only accumulate raw data and
leave compiled understanding stale.

This session introduces the trigger model that keeps the compiled layer live.

## Goal

Build the first connector-driven compilation trigger system that:

1. reacts to source-truth changes
2. determines which compiled outputs need refresh
3. triggers targeted recompilation
4. avoids recompiling the whole brain unnecessarily
5. stays additive and compatible with the current production memory path

This is the session that makes connector ingestion high-leverage.

## Non-Goals

- Do not build every connector in this session.
- Do not redesign the capture pipeline broadly.
- Do not replace the existing production memory path.
- Do not add new foundational dependence on Hindsight or Graphiti.
- Do not implement a full UI/browser layer here.
- Do not build a global “recompile everything” cron as the main design.

## Strategic Intention

HAETSAL should not compile on a purely manual basis.

The long-term brain needs:

- durable source truth
- generated understanding
- automatic refresh when new knowledge arrives

This session introduces the middle layer that maps:

- changed source truth

to:

- affected compiled outputs

to:

- targeted compile jobs

## Required Behavior

### 1. Detect source-truth changes

When canonical truth changes, the system should be able to identify the event as
something that may invalidate or refresh compiled outputs.

This should work for at least:

- new canonical captures
- updated canonical documents/artifacts where relevant
- future connector-driven writes through the canonical path

### 2. Determine affected compile targets

The trigger system should decide what to refresh.

At minimum, it should support targeting:

- dossiers affected by the changed truth
- context packs affected by the changed truth
- change-oriented views affected by the changed truth

This targeting does not need to be perfect in v1, but it should be clearly
better than “compile everything.”

### 3. Queue targeted recompilation

The trigger system should enqueue or invoke compilation jobs for the affected
targets in a way that is:

- additive
- incremental
- queue/workflow friendly

### 4. Preserve regeneration-safe semantics

Recompilation should update the same stable compiled identities where
appropriate, not create conceptual duplicates.

## Suggested Trigger Model

The minimal model should include:

### Change event

A compact event describing:

- tenant
- changed canonical record(s)
- change type
- relevant scope
- relevant subject hints if known

### Affected target planner

A small planner that maps change events to candidate compiled targets, such as:

- dossier stable keys
- context-pack stable keys
- change-view stable keys

### Compilation dispatch

A queue- or service-friendly dispatch step that invokes the existing compiler
for those specific targets.

## Identity / Planning Rules

This session should define a first explicit rule set for refresh targeting.

Examples:

- a changed project-related capture should refresh:
  - that project dossier
  - relevant project context packs
  - recent change view

- a changed person-related capture should refresh:
  - that person dossier
  - relevant handoff or Chief-of-Staff context packs

- a capture with no strong typed target may at least refresh:
  - tenant-level recent change view

The exact heuristics can be simple in v1, but they should be explicit and
documented.

## Service Boundaries

Introduce or refine seams for:

- change-event extraction
- compile-target planning
- targeted compile dispatch

Keep these pieces:

- small
- testable
- future queue/workflow compatible

Avoid embedding all trigger logic deep inside one existing service if a small,
clear trigger module is possible.

## Product-Surface Expectations

This session should mostly be internal.

Allowed:

- internal queue/job wiring
- tiny debug/readback helpers if truly needed

Avoid:

- broad user-facing tool expansion
- major MCP redesign
- connector UX in this session

The point is to make connectors viable, not to ship all connectors yet.

## Verification

Add or tighten tests for:

- canonical change event creates targeted compile plans
- targeted compile plans include the right dossier/context-pack/change targets
- recompilation dispatch is invoked for those targets
- repeated changes preserve stable compiled identities
- the existing production memory path remains intact

Run at minimum:

- dedicated `11.4` test file(s)
- relevant 11.0 / 11.1 / 11.2 / 11.3 tests
- relevant canonical/Postgres tests

## Local Proof

Before finishing:

- verify a canonical write can trigger targeted compile planning
- verify at least one dossier/context-pack/change target is refreshed
- verify existing production memory flows remain functional
- explicitly state whether any compatibility shim was required

## Deliverable

At the end of this session, HAETSAL should have:

1. a source-change -> compile-target planning layer
2. targeted compilation dispatch
3. incremental freshness behavior for compiled outputs
4. a clean base for plugging real connectors into the MCP/brain
5. a clear next step into the first connector ingestion sessions

- **Change-Event -> Target-Planning Model Shipped**
  - Added a compact internal canonical compiled-change event shape carrying:
    - tenant
    - change type
    - scope
    - source system/ref/title
    - changed canonical capture/document/artifact/operation ids
    - explicit subject hints when detectable
  - 11.4 now emits this event from the canonical capture path after a new canonical write is accepted.
  - The current subject-hint extractor is intentionally explicit and small:
    - only project-scoped canonical writes plan compiled refreshes in 11.4
    - project identity prefers the first stable `sourceRef` segment when present
    - title/body cues are fallback hints when `sourceRef` is not enough
  - The resulting project subject hint maps to the same stable-key family already used by 11.2 / 11.3:
    - `entity:project:{slug}`

- **Targeting Heuristics Landed**
  - For a detected project-scoped canonical change, the planner now explicitly creates candidate refresh targets for:
    - `dossier:project:{slug}`
    - `context-pack:project:{slug}`
    - `what-changed:project:{slug}`
  - This is deliberately better than "compile everything" while still staying understandable and regeneration-safe.
  - If no supported project hint is detected, the trigger emits no compiled targets rather than widening into a global recompile.

- **Targeted Recompilation Dispatch**
  - Added `dispatchTargetedCompiledRefresh`, which groups the planned project targets into one `project_compilation` dispatch job and reuses the existing `compileProjectSynthesisFromCanonicalTruth` seam.
  - This preserves stable compiled identities because dispatch reuses the same subject stable key and the same compiled-document stable keys already established by 11.2:
    - dossier
    - project context pack
    - project `what_changed`
  - Dispatch remains queue/workflow compatible in shape, but 11.4 intentionally invokes the existing internal compiler directly rather than introducing a new queue contract prematurely.
  - TMK availability is now the explicit gate for targeted refresh, because the compiler reads canonical source bodies from encrypted R2 through the existing canonical read path.

- **Canonical Capture Wiring**
  - `captureThroughCanonicalPipeline` now calls a small `maybeTriggerCompiledRefresh` seam after the existing compatibility retain bridge work is scheduled.
  - When an execution context exists, targeted compilation is handed to `waitUntil()` so the write path stays additive.
  - When no execution context exists, the trigger can still run inline for tests and internal direct calls.
  - `retainContent` now passes the active TMK through to the canonical pipeline so connector-like writes that already have an active session key can trigger targeted recompilation without redesigning the production path.
  - `captureCanonicalMemory` / `CanonicalCaptureResult` now return `artifactId` so the change event can carry fuller canonical record linkage.

- **Compiled Target Families Now Refreshable Incrementally**
  - `project_dossier`
  - `project_context_pack`
  - `what_changed` for project subjects

- **What Was Intentionally Preserved**
  - The existing production memory path stayed intact.
  - The canonical capture / projection queue path stayed intact.
  - The compatibility retain bridge stayed intact.
  - No "recompile everything" fallback cron or broad capture-pipeline redesign was introduced.
  - No new foundational dependence on Hindsight or Graphiti was added.
  - Stable regeneration-safe compiled identities remained anchored to the existing 11.2 compiled stable keys and source-fingerprint artifact versioning.
