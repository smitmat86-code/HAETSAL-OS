## What We're Building

Make Graphiti project **real entities and relationships from capture body
content**, not just canonical episode/source/scope scaffolding.

Session 9.6 proved that Graphiti now runs internally inside HAETSAL and that
fresh captures reach the internal Graphiti runtime in production.

But live proof also showed that the current graph output is still too shallow:

- graph jobs complete
- graph identity mappings are written
- but the graph mostly contains:
  - episode anchors
  - source anchors
  - scope anchors
  - structural edges such as `captured_via` and `within_scope`

It does **not yet** materialize enough body-derived graph structure for:

- `trace_relationship`
- `get_entity_timeline`
- graph-enhanced `prepare_context_for_agent`

to deliver the richer graph capability we expect.

This session closes that gap.

---

## Why This Session Exists

The post-9.6 live acceptance sweep established the new baseline:

- Graphiti runtime topology is now correct.
- Graphiti handoff is now live.
- Graphiti projection jobs now complete.
- Graph identity mappings now persist in production.

But the same live sweep also showed:

- `trace_relationship` returns zero edges for fresh body facts
- `get_entity_timeline` returns zero timeline events for fresh body facts
- `prepare_context_for_agent` still falls back to raw/semantic memory for
  those same facts

So the remaining missing piece is no longer runtime topology.
It is **graph semantic richness**.

This session should make Graphiti worthy of its role as the graph/temporal
engine rather than just a projection-status sidecar.

---

## Strategic Answer

### What is wrong today?

The current graph projection plan is too conservative. It reliably emits:

- canonical episode
- canonical scope
- canonical source
- deterministic structural edges

but it does not yet emit enough **body-derived entities** and
**body-derived relations** to support meaningful graph queries from natural
captures.

### What should be added?

For the first real graph-capability step, body-derived graph projection should
at minimum support:

- person entities
- organization / project entities
- note-level fact relations such as:
  - `leads`
  - `partnered_with`
  - `met_with`
  - `depends_on`
  - similarly narrow first-rollout relations if naturally supported

### Is this “full upstream Graphiti”?

No.

This session should make HAETSAL’s current graph surface actually useful and
credible. It is not required to expose every upstream Graphiti capability or
rebuild Graphiti’s entire ontology model in one pass.

The focus is:

- enough body extraction to make HAETSAL graph reads materially better than raw
  fallback alone
- enough temporal/relationship structure to justify the graph engine in the
  product

## Behavioral Wiring

### Projection Behavior

Fresh captures should continue to project:

- episode anchor
- scope anchor
- source anchor

But now also, when body content supports it:

- person / org / project / topic entities derived from body semantics
- relation edges derived from body semantics
- temporal edges or timestamped observations when the body expresses them

### Query Behavior

After projection completes:

- `trace_relationship` should return body-derived graph edges when present
- `get_entity_timeline` should return body-derived timeline observations when
  present
- `prepare_context_for_agent` should be able to cite graph-derived
  relationships/timeline items rather than only raw/semantic evidence

### Failure Behavior

- if body extraction is sparse or ambiguous, canonical graph projection should
  remain truthful and partial
- do not fake graph richness where extraction confidence is absent
- preserve the existing deterministic scaffold even when richer extraction
  fails or is skipped

---

## First-Rollout Extraction Targets

The first rollout should focus on a narrow but high-value set of graph facts.

### Entity Classes

- `person`
- `organization`
- `project`
- `topic` when clearly useful

### Relation Classes

- `leads`
- `partnered_with`
- `met_with`
- `depends_on`

Exact internal naming may differ, but the behavior should support these kinds
of facts from natural note-style captures.

### Temporal Signals

When a capture body includes an explicit date/time signal, preserve it so:

- entity timelines can show meaningful observations
- relations that happened “on” a date are not flattened into timeless edges

This should be narrow and truthful, not an attempt at a full event ontology.

## Part 3: Runtime / Extraction Contract

The internal Graphiti runtime should be able to accept enough semantic content
to produce richer graph outputs than the current scaffold-only behavior.

The resulting response may extend or deepen fields already present in the
internal Graphiti contract, such as:

```typescript
export interface InternalGraphitiProjectionResponse {
  status: 'queued' | 'completed'
  targetRef?: string | null
  operationRef?: string | null
  episodeRefs?: string[]
  entityRefs?: string[]
  edgeRefs?: string[]
  mappings?: Array<{
    canonicalKey: string
    graphRef: string
    graphKind: 'episode' | 'entity' | 'edge'
  }>
}
```

The important change is behavioral:

- `mappings` should now include meaningful body-derived entity/edge mappings
  when extraction succeeds

not just episode/source/scope scaffolding.
