# Session 11.7 - Post-Hindsight Projection Policy Surface

Status: Completed
Owner: Codex
Date: 2026-06-04

## Why This Session Exists

Session 11.6 added a production-neutral working-session summary capture bridge.
Before that bridge can be wired into real canonical capture, HAETSAL needs an
explicit projection-lane policy surface.

Canonical capture already writes HAETSAL-owned memory to the canonical
Postgres/R2 boundary, but it previously assumed that every accepted capture
should create both Hindsight and Graphiti projection jobs. That was correct for
the compatibility phase, but post-Hindsight capture needs a way to write
canonical truth while selecting Graphiti without materializing or dispatching a
Hindsight projection payload.

## Goal

Add an explicit projection selection surface to canonical capture and the
canonical capture pipeline:

1. callers may pass `projectionKinds`
2. omitted `projectionKinds` preserves the existing Hindsight plus Graphiti
   default
3. `projectionKinds: ["graphiti"]` creates only Graphiti projection jobs
4. pipeline dispatch payloads reflect the selected lanes
5. projection payload materialization runs only for selected lanes
6. the returned pipeline capture state reports the selected lanes
7. post-Hindsight callers can combine Graphiti-only projection with
   `compatibilityMode: "off"`

## Boundary

This phase is policy-surface only.

- Did not wire the new surface to production agents.
- Did not wire the new surface to MCP tools, routes, Durable Objects, or the
  working-session capture bridge.
- Did not remove Hindsight globally.
- Did not change Cloudflare bindings or deployment configuration.
- Did not deploy.
- Did not change `wrangler.toml`.
- Did not adopt Cloudflare Sessions, Think, AI Chat, Shell,
  workers-ai-provider, or Hindsight primitives.

## Implementation

Extended canonical capture contracts:

- `CanonicalCaptureInput.projectionKinds`
- `CanonicalPipelineCaptureInput.projectionKinds`
- `CanonicalCaptureResult.projectionKinds`

Added `resolveCanonicalProjectionKinds()` in
`src/services/canonical-memory-schema.ts`.

The resolver:

- returns a copy of `CANONICAL_PROJECTION_KINDS` when omitted
- validates explicit lanes against the supported canonical projection kinds
- de-duplicates explicit selections
- rejects empty explicit selections

Updated `captureCanonicalMemory()` so canonical projection jobs are created
from the resolved lanes instead of the hardcoded default list.

Updated `captureThroughCanonicalPipeline()` so the selected lanes drive:

- the `captureCanonicalMemory()` input
- the queued dispatch message payload
- Hindsight projection payload materialization
- Graphiti projection payload materialization
- returned `capture.projectionKinds`

Hindsight projection payload materialization now runs only when the selected
lanes include `hindsight`.

Graphiti projection payload materialization now runs only when the selected
lanes include `graphiti`.

The existing projection consumer already honored the dispatch payload's
`projectionKinds`, so no production consumer wiring changed.

## Tests

Added
`tests/11.7-post-hindsight-projection-policy-surface.test.ts`.

The tests prove:

- omitted `projectionKinds` preserves Hindsight plus Graphiti jobs, dispatch
  payloads, materialized payloads, and current compatibility default
- `projectionKinds: ["graphiti"]` creates only a Graphiti projection job and
  dispatch lane
- Graphiti-only with `compatibilityMode: "off"` skips Hindsight compatibility
- eager Graphiti-only dispatch completes Graphiti projection without invoking
  Hindsight dispatch and without writing a Hindsight projection payload
