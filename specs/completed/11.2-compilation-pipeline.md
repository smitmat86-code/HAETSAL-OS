# Session 11.2 - Compilation Pipeline

Status: Active
Owner: Codex
Date: 2026-04-22

## Why This Session Exists

Session 11.0 established the compiled-synthesis storage foundation.

Session 11.1 refined the object model for:

- dossiers
- context packs
- contradiction objects
- decision/change views

What does not yet exist is the mechanism that actually turns canonical truth
into those compiled outputs.

This session builds the first real HAETSAL compiler.

## Goal

Build the first compilation pipeline that:

1. reads canonical truth from Neon/Postgres
2. produces the first meaningful compiled outputs
3. persists structured compiled records back to Postgres
4. writes renderable artifacts to R2
5. stays additive without cutting over the full read path yet

The result should be the first real end-to-end HAETSAL-native synthesis loop.

## Non-Goals

- Do not redesign the Chief of Staff interaction flow yet.
- Do not broadly replace the current production memory path yet.
- Do not add new foundational reliance on Hindsight or Graphiti.
- Do not attempt to compile every possible artifact family in this session.
- Do not turn this into a generic “LLM summarize everything” pass.

## Strategic Intention

The compiler is the heart of re-aligned HAETSAL.

It should not produce vague summaries.

It should produce durable, regenerable, typed compiled outputs that are:

- useful to humans
- useful to agents
- clearly linked to source truth
- safe to regenerate over time

This is where HAETSAL begins to own its own intelligence layer.

## Scope

This session should implement the first practical compile targets.

### Required initial compile families

At minimum, implement compilation for:

1. dossier family
   - at least one concrete dossier type should compile end-to-end
   - recommended starting point:
     - `topic_dossier`
     - or `project_dossier`

2. context pack family
   - at least one concrete context-pack type should compile end-to-end
   - recommended starting point:
     - `project_context_pack`
     - or `chief_of_staff_context_pack`

3. change-oriented view
   - at least one `what_changed` or equivalent change digest should compile

Contradiction compilation may be limited to a first simple pass if needed, but
the session should leave a clear place for it.

## Pipeline Requirements

### Inputs

The compiler should read from:

- canonical captures
- canonical documents
- canonical chunks
- canonical artifacts where relevant
- any refined compiled-family seeds/identities from 11.1

It should use existing canonical truth, not bypass it.

### Outputs

The compiler must produce:

- structured compiled records in Postgres
- rendered artifacts in R2

At minimum, artifact output should include:

- JSON for agent-ready consumption
- Markdown for human-readable consumption

HTML may remain deferred if not needed yet.

### Regeneration semantics

The compiler must preserve:

- stable identity for compiled objects
- version-safe regeneration
- traceable linkage to source truth

Regeneration should update the current compiled view without making the object
conceptually “new” every run.

### Source linkage

Every compiled object produced in this session must retain clear linkage to:

- contributing canonical records
- rendered R2 artifacts
- compilation timestamps / versioning markers

## Triggering Model

This session should introduce the first compilation triggering path.

Acceptable starting patterns:

- explicit internal service call
- queue-driven compile trigger
- targeted compile job invocation for tests

Preferred direction:

- queue-compatible and future Workflow-compatible

But keep the implementation as small as possible in this session.

## Service Boundaries

Introduce clear seams for:

- selecting source truth for compilation
- constructing compiled object payloads
- persisting structured compiled records
- rendering/writing artifacts

Recommended shape:

- input selection layer
- compile/assemble layer
- persistence/render layer

Avoid turning this into one giant function.

## Rendering Expectations

### Markdown

Markdown outputs should be:

- concise
- stable in layout
- suitable for direct human reading
- suitable for future note/wiki-style browsing

### JSON

JSON outputs should be:

- compact
- typed enough for agents
- directly reusable by future context builders

### Content expectations

Compiled outputs should favor:

- explicit facts
- relationships
- recent changes
- unresolved questions
- contradictions where known
- actionability

over:

- generic prose
- long essay summaries
- low-signal repetition

## Verification

Add or tighten tests for:

- end-to-end dossier compilation from canonical truth
- end-to-end context-pack compilation from canonical truth
- end-to-end change-view compilation from canonical truth
- Postgres compiled record persistence
- R2 JSON artifact output
- R2 Markdown artifact output
- stable regeneration-safe identity across repeated compilation runs
- correct source linkage from compiled outputs back to canonical truth

Run at minimum:

- relevant 11.0 / 11.1 compiled-synthesis tests
- relevant canonical/Postgres tests
- `npm test`

Before finishing:

- verify at least one dossier and one context pack can be compiled and read back
  locally
- verify the rendered artifacts exist in R2 with the intended layout
- explicitly state whether any compatibility shim was required

## Deliverable

At the end of this session, HAETSAL should have:

1. a working first compiler
2. at least one dossier compiled end-to-end
3. at least one context pack compiled end-to-end
4. at least one change-oriented compiled view
5. Postgres + R2 outputs that future read paths can consume
6. a clean handoff to:
   - `11.3` Chief of Staff compiled read path

- **First Real Compiler Path Added**
  - Introduced `compileProjectSynthesisFromCanonicalTruth` as the first explicit internal HAETSAL compiler trigger.
  - The trigger stays small and additive: it takes `tenantId`, a typed project subject, and a caller-supplied `tmk`, then compiles three outputs in one pass:
    - `project_dossier`
    - `project_context_pack`
    - `what_changed`
  - This is queue-compatible / Workflow-compatible later, but 11.2 keeps the trigger as a direct internal service call plus targeted test invocation.

- **Service Boundary Shape Landed**
  - **Source-truth selection layer**
    - `compiled-synthesis-source-truth.ts` now selects recent canonical documents from Neon/Postgres by scope, hydrates their canonical bodies from R2 using the canonical body pointer, scores them against the project subject/keywords, and produces stable source refs plus a deterministic source fingerprint.
  - **Compile / assemble layer**
    - `compiled-synthesis-signal-*` modules parse explicit structured signals out of canonical bodies:
      - facts
      - relationships
      - recent changes
      - decisions
      - open questions
      - actions
      - contradictions
    - `compiled-synthesis-assemble*.ts` turns those parsed signals into typed compiled dossier/context-pack/change-view payloads and supporting compiled entity/fact/relationship/contradiction rows.
  - **Persistence / render layer**
    - `compiled-synthesis-render*.ts` renders stable markdown + compact JSON artifacts.
    - Existing 11.0 / 11.1 persistence seams were reused unchanged:
      - `persistCompiledSynthesis`
      - compiled Postgres store/repository
      - compiled artifact R2 writer

- **End-to-End Families Now Compiling**
  - **Dossier family**
    - `project_dossier`
  - **Context-pack family**
    - `project_context_pack`
  - **Change-oriented compiled view**
    - `what_changed`
  - These now compile from canonical truth through:
    - source selection
    - typed assembly
    - Postgres compiled record writes
    - R2 artifact rendering
    - typed readback via existing compiled-synthesis readers

- **Artifact Formats Now Rendering To R2**
  - Dossier:
    - `dossier_markdown`
    - `dossier_json`
  - Context pack:
    - `context_pack_markdown`
    - `context_pack_json`
  - Change view:
    - `what_changed_markdown`
    - `what_changed_json`
  - Existing deterministic compiled artifact layout from 11.0 was preserved:
    - `compiled/{tenantId}/{family}/{stableKey}/{artifactRole}/{version}.{ext}`

- **Regeneration-Safe Identity / Versioning**
  - Stable compiled identity is preserved with deterministic document stable keys:
    - `dossier:project:{subject}`
    - `context-pack:project:{subject}`
    - `what-changed:project:{subject}`
  - Supporting dossier rows keep stable keys derived from subject + semantic role:
    - facts
    - relationships
    - contradictions
    - entities
  - Artifact versioning is derived from a deterministic fingerprint of the selected canonical source set.
    - Re-running compilation against the same selected source truth keeps the same conceptual identity and artifact version.
    - Re-running after canonical truth changes preserves conceptual identity but writes a new source-derived artifact version.

- **Source Linkage Back To Canonical Truth**
  - Every compiled document now writes:
    - `compiled_document_sources` rows linked to contributing canonical capture/document/artifact ids
    - section-level `sourceRefs` pointing back to canonical ids and body R2 keys
    - compiled artifact refs in `compiled_document_artifacts`
  - This gives each compiled output:
    - canonical provenance
    - rendered artifact linkage
    - source-fingerprint-backed regeneration markers

- **Intentionally Preserved Existing Work**
  - The current production memory path was not rerouted or replaced.
  - Chief of Staff runtime interaction flow was not redesigned.
  - No new foundational Hindsight or Graphiti reliance was added.
  - The canonical capture/document/artifact model remained the source truth.
  - Existing compiled-synthesis 11.0 / 11.1 storage and read seams were preserved rather than redesigned.
  - Supporting compiled entity/fact/relationship/contradiction rows remain anchored to the dossier document so 11.2 did not destabilize the multi-family read model.
