# Session 11.0 - HAETSAL Compiled Synthesis Foundation

Status: Active
Owner: Codex
Date: 2026-04-22

## Why This Session Exists

HAETSAL is being re-aligned around its original product intent:

- a personal open brain
- durable memory you take with you
- compounding understanding over time
- custom agents and workflows on top
- a Chief of Staff as the primary operator/front door, without making the brain
  dependent on a single agent persona

The current Hindsight/Graphiti-centered direction proved too operationally
fragile and too architecturally heavy for this product goal.

The next step is to establish the new center of gravity:

- durable structured truth in Neon/Postgres
- raw and generated artifacts in R2
- HAETSAL-native compiled synthesis as the main intelligence layer

This session defines and lands that foundation.

## Goal

Introduce the first-class compiled-synthesis foundation for HAETSAL:

1. keep Neon/Postgres + R2 as the durable substrate
2. define the first canonical compiled-output record families
3. create the storage and service seams required for compilation output
4. do this without broad product-surface redesign yet
5. do this without adding new foundational dependency on Hindsight or Graphiti

This is a foundation session, not a full compiler session.

## Non-Goals

- Do not build the full compiler yet.
- Do not redesign the Chief of Staff interaction flow yet.
- Do not remove the current production memory path yet.
- Do not add new reliance on Hindsight or Graphiti.
- Do not add broad search/index/graph features in this session.
- Do not turn this into a wiki product first.

## Strategic Direction

HAETSAL should move from:

- multi-engine memory substrate thinking

to:

- durable structured brain
- compiled understanding
- agent-ready context assets

The compiled layer should be HAETSAL-owned and regenerable.

## Foundation Principles

1. Neon/Postgres is the authoritative structured truth store.
2. R2 is the authoritative raw and generated artifact shelf.
3. Compiled outputs are derived artifacts, not hand-edited truth.
4. The compiled layer must support both:
   - human-readable outputs
   - agent-usable context objects
5. The Chief of Staff is a primary consumer of the compiled layer, but not its
   sole reader/writer.
6. Other agents, workflows, and direct working sessions must remain first-class
   participants in the same brain.

## What Must Be Introduced

This session should introduce the minimum schema/service foundation for the
compiled layer.

### New Record Families

At minimum, define the first compiled-synthesis families:

- `compiled_entities`
- `compiled_facts`
- `compiled_relationships`
- `compiled_contradictions`
- `compiled_documents`
- `compiled_context_packs`

The names may differ if a better schema naming convention is chosen, but the
conceptual coverage should remain.

### Required Properties

Each compiled object should be able to answer:

- what source truth records contributed to this artifact?
- what scope does it belong to?
- when was it compiled?
- what kind of compiled object is it?
- where is the rendered artifact, if any?
- can an agent use this directly as context?

### Artifact Outputs

The foundation should support compiled artifacts in R2 such as:

- markdown dossiers
- json context objects
- html briefings later

This session does not need to generate all of them yet, but it must define the
path and backing model clearly.

## Expected Architectural Changes

### Postgres

Add the first canonical synthesis-oriented tables/schemas required to support:

- entities
- facts
- relationships
- contradictions
- context packs
- synthesis document metadata

This can be done as:

- new tables inside the existing canonical schema
- or a clearly named adjacent schema

The choice should be made for long-term readability and durability, not for
short-term convenience.

### R2

Define how generated compiled artifacts are stored and referenced.

At minimum, support:

- deterministic keys
- versioned/regenerable artifacts
- mapping from compiled Postgres records to R2 objects

### Services

Create the first service/repository seam(s) for compiled-synthesis records and
artifact references.

These should be:

- explicit
- testable
- small
- compatible with future compiler jobs

## What Existing Work Should Be Preserved

Keep and reuse where it still fits:

- canonical capture/document/artifact model
- Postgres source-of-truth work
- R2 artifact handling patterns
- MCP-first interface discipline
- operation/provenance modeling

The goal is not to discard good foundation work. The goal is to redirect the
center of the architecture.

## Minimal Product-Surface Expectation

This session may add:

- internal read/write services
- internal types
- internal repository methods

It should avoid broad new user-facing tools unless a tiny debug/readback surface
is necessary for verification.

This is a foundation session.

- compiled record creation in Postgres
- compiled artifact reference creation
- R2 linkage for generated artifacts
- provenance linkage from compiled outputs back to canonical truth
- context-pack record storage
- regeneration-safe identity behavior

Run at minimum:

- dedicated `11.0` tests

- `npm test`

## Live Expectations

Do not require a full product cutover in this session.

But verify that:

- current production memory path is not broken by the added foundation work
- current production read/write flows still function locally

If any compatibility shim is needed, keep it narrow and document it explicitly
in As-Built.

## Deliverable

At the end of this session, HAETSAL should have:

1. a real compiled-synthesis foundation in Neon/Postgres + R2
2. explicit record families for compiled outputs
3. clear references between structured truth and generated synthesis artifacts
4. no new foundational dependence on Hindsight/Graphiti
5. a clean base for:
   - `11.1` dossier/context-pack schema refinement
   - `11.2` compilation pipeline
   - `11.3` Chief of Staff compiled read path

- **Durable Model / Linkage**
  - Compiled outputs live in the existing `haetsal_canonical` Postgres schema beside the current canonical capture/document/artifact truth model.
  - `compiled_documents` provides the stable compiled identity (`stable_key`, family, scope, audience, compiled timestamp) for each compiled output unit.
  - `compiled_document_sources` links compiled outputs back to canonical truth via canonical capture/document/artifact/operation ids.
  - `compiled_document_artifacts` links compiled outputs to deterministic, versioned R2 artifact keys for generated markdown/json/html outputs.
  - The family tables (`compiled_entities`, `compiled_facts`, `compiled_relationships`, `compiled_contradictions`, `compiled_context_packs`) attach structured synthesis records to a compiled document and keep stable identities across regeneration via tenant-scoped `stable_key` upserts.

- **R2 Layout Decision**
  - Generated compiled artifacts now use deterministic keys under:
    - `compiled/{tenantId}/{family}/{stableKey}/{artifactRole}/{version}.{ext}`
  - This preserves stable compiled identity while allowing multiple regenerations/versions per compiled document.

- **Preserved Existing Work**
  - The current canonical capture/document/artifact model remained untouched.
  - The current production memory read/write path remained untouched.
  - Existing Neon/Postgres + R2 substrate reuse was preserved.
  - No new foundational dependency on Hindsight or Graphiti was added.
  - No Chief of Staff flow redesign was attempted in 11.0.

- **Service / Repository Seams Added**
  - `compiled-synthesis-repository` adds explicit in-memory + Neon repository seams for compiled documents, source links, artifact refs, and family records.

  - `compiled-synthesis-artifacts` owns deterministic compiled R2 key construction and artifact persistence.
  - `persistCompiledSynthesis` / `readCompiledSynthesis` provide the first small orchestration/read seam future compiler jobs can call directly.
