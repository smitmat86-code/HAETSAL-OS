## What We're Building

Introduce the first explicit **open-brain broker** as the default read path for
HAETSAL.

Today HAETSAL already has:

- canonical query tools
- a retrieval router
- Hindsight semantic recall
- Graphiti graph/timeline reads
- composed context assembly

What it does **not** yet have is an explicit broker contract that:

- chooses a primary engine/mode for the user-facing result
- also runs the secondary engine in the background
- records the comparison for the tenant
- keeps user-facing behavior simple while collecting evidence for later routing
  and synthesis improvements

Session 9.8 adds exactly that.

This session is intentionally **not** the full future orchestration layer.
It is the smallest useful broker:

- primary result on the hot path
- shadow-secondary retrieval in the background
- tenant-visible trace capture
- no user-facing cross-engine synthesis yet

---

## Why This Session Exists

The target architecture says:

- canonical storage becomes the source-of-truth foundation over time
- Hindsight is the semantic engine
- Graphiti is the graph/temporal engine
- Cloudflare is the runtime and orchestration shell

That implies HAETSAL needs an explicit broker layer above the engines.

We do **not** want to jump straight to:

- fully merged dual-engine answers
- broad platform analytics
- large learned routing systems

We do want to:

- keep the user-facing path simple
- preserve engine-native power underneath
- gather real query-by-query evidence about what each engine contributed

Session 9.8 is the first deliberate step into that broker architecture.

## Strategic Scope

### In Scope

- broker default read path
- primary route selection
- background shadow-secondary retrieval
- tenant-scoped rich trace capture for the active tenant/user
- broker use in canonical search and context assembly entrypoints
- live acceptance proving Hindsight and Graphiti remain green

### Explicitly Out of Scope

- canonical Postgres migration
- platform-owner anonymized telemetry product
- route-learning automation
- user-facing synthesized dual-engine answers
- broad public exposure of native Hindsight/Graphiti expert surfaces

Those come later.

## THE Brain Laws Check

### Law 1: One Public Face

The broker must sit behind the existing McpAgent/Worker canonical surface. This
session must not add a new public engine-specific API.

### Law 2: Zero-Knowledge

The broker may record rich tenant-scoped traces, but it must not create new
raw-content caches in D1, KV, or Analytics Engine. Any detailed tenant trace
that stores richer payloads must use the trusted canonical storage strategy and
artifact/archive surfaces only.

### Law 3: Agent Write Policy

This is a read/broker/trace session. It must not widen memory write authority or
action authority.

## Behavioral Wiring

### Authorization

| Route / Entry Point | Auth Level | Tenant ID Source | When Checked |
|---------------------|-----------|-----------------|-------------|
| Canonical search tools via McpAgent | Existing auth/session path | Existing tenant context | Existing auth middleware + DO bootstrap |
| `prepare_context_for_agent` via McpAgent | Existing auth/session path | Existing tenant context | Existing auth middleware + DO bootstrap |
| Internal broker service | Trusted internal caller | Service arg / tenant context | At service boundary |
| Tenant trace readback (if surfaced in-session) | Existing auth/session path | Existing tenant context | Existing auth middleware + DO bootstrap |

No intentionally public route is added in this session.

### Action Layer

No action tools in this session.

### Audit / Trace

| Event | Store | Purpose | Blocking? |
|-------|-------|---------|-----------|
| Broker primary route decision | Tenant trace lane | Per-query trace | Non-blocking |
| Shadow-secondary completion/failure | Tenant trace lane | Per-query trace | Non-blocking |
| Broker timeout / skipped shadow | Tenant trace lane | Diagnostic trace | Non-blocking |

This is **tenant trace**, not a broad platform analytics product. The trace must
be attributable to the tenant and readable by that tenant later.

### Compute Routing

| Operation | Tier | Rationale |
|-----------|------|-----------|
| Primary route selection | Sync Worker / service | User-facing query contract |
| Primary retrieval | Existing sync read path | Hot path |
| Shadow-secondary retrieval | Background non-blocking task via `waitUntil` or equivalent | Do not add user-visible latency |
| Tenant trace persistence | Background non-blocking task | Read telemetry, not hot path |

### Other Behavioral Wiring

- The broker should reuse the existing explainable router from Session 9.1
  rather than inventing a new opaque planner.
- A broker query should have a stable query id / trace id.
- The broker should preserve the current user-facing answer shape where possible.
- The shadow-secondary path must be read-only.
- If the shadow-secondary path times out or fails, the primary result still
  succeeds unless the primary path itself failed.

## Part 3: Types / Contract

The broker contract should define shapes along these lines:

```typescript
export type BrokerPrimaryMode = 'raw' | 'semantic' | 'graph' | 'composed'

export interface BrokerRouteDecision {
  queryId: string
  primaryMode: BrokerPrimaryMode
  shadowMode: Exclude<BrokerPrimaryMode, 'raw' | 'composed'> | BrokerPrimaryMode
  reason: string
  explicit: boolean
}

export interface BrokerTraceSummary {
  queryId: string
  tenantId: string
  queryText: string
  primary: {
    mode: BrokerPrimaryMode
    status: 'ok' | 'empty' | 'error'
    latencyMs: number
    summary: string
  }
  shadow: {
    mode: BrokerPrimaryMode
    status: 'ok' | 'empty' | 'error' | 'timeout' | 'skipped'
    latencyMs?: number
    summary?: string
  }
  overlap: 'same' | 'partial' | 'distinct' | 'unknown'
}
```

Exact names may differ, but the session must answer:

- what was the primary path?
- what was the shadow path?
- what did each path return?
- what was shown to the user?

## Part 4: Broker Behavior

### Primary Route

The broker should use the Session 9.1 router to pick the primary mode.

Recommended default mapping:

- raw -> primary raw, no shadow required by default
- semantic -> primary Hindsight semantic, shadow Graphiti
- graph -> primary Graphiti, shadow Hindsight semantic
- composed -> primary composed/context path, shadow whichever engine was not the
  dominant contributor

If the implementation needs a narrower first rollout, the minimum required
broker behavior is:

- semantic primary -> graph shadow
- graph primary -> semantic shadow

### Shadow Route

The shadow route must:

- be read-only
- run in the background
- have a short bounded timeout
- capture useful trace data even when incomplete

The shadow route must **not**:

- block the user-facing response
- re-rank the primary result in this session
- mutate memory, graph, or reflection state

### User-Facing Behavior

The user should continue receiving the primary answer shape only.

This session must not silently turn every query into a merged synthesis.

---

## Part 5: Tenant Trace

This session is explicitly **tenant-first**, not platform-first.

### Tenant-visible detail should include

- exact query text
- primary route chosen
- what the primary route returned
- what the shadow route returned
- what the broker surfaced to the user
- timing and route reason

### Tenant trace storage principles

- full detail is allowed for the tenant's own traces
- traces must remain tenant-scoped
- richer payloads should use the trusted canonical artifact/archive pattern if
  they exceed the structured store's right size

### Platform/privacy boundary

This session must not create a broad platform-owner surface to inspect raw
tenant traces. That is a later, separate, anonymized product concern.
