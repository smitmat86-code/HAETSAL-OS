# Session 11.1 - Dossier And Context Pack Schema Refinement

Status: Active
Owner: Codex
Date: 2026-04-22

## Why This Session Exists

Session 11.0 established the compiled-synthesis foundation for re-aligned
HAETSAL:

- compiled record families now exist in Neon/Postgres
- compiled artifacts can be referenced in R2
- provenance links back to canonical truth are in place

What does **not** yet exist is a sufficiently sharp definition of what HAETSAL
is actually compiling for human and agent use.

This session defines that object model.

The goal is to make HAETSAL's compiled outputs concrete enough that the next
compiler session (`11.2`) can generate them deliberately rather than producing
generic summaries with weak semantics.

## Goal

Define and land the first clear schema/read-model refinement for HAETSAL's
compiled outputs, especially:

1. dossiers
2. context packs
3. contradiction objects
4. decision/change-oriented summaries

This session should make the compiled layer more specific, more queryable, and
more useful for both:

- human browsing
- agent consumption

## Non-Goals

- Do not build the full compiler yet.
- Do not redesign the Chief of Staff conversation flow yet.
- Do not cut over the main production read path yet.
- Do not add new foundational dependence on Hindsight or Graphiti.
- Do not turn compiled outputs into a manually edited wiki.

## Strategic Intention

HAETSAL's compiled layer should not be "a pile of summaries."

It should produce a small number of durable, legible, regenerable object types
that become the main semantic surface for:

- the Chief of Staff
- specialist agents
- direct working sessions
- future project integrations

That means the shape of these objects matters.

## Core Output Families

This session should refine at least the following families into clear
first-class models.

### 1. Dossiers

Dossiers are stable synthesized views over a subject.

Initial dossier families should include:

- `person_dossier`
- `project_dossier`
- `topic_dossier`

Each dossier should answer:

- who/what is this?
- why does it matter?
- what is the current state?
- what are the important relationships?
- what recent changes matter?
- what open questions/risks/unknowns remain?
- what source truth backs this?

### 2. Context Packs

Context packs are compact, task- and agent-usable bundles.

Initial context-pack families should support:

- `chief_of_staff_context_pack`
- `project_context_pack`
- `person_context_pack`
- `session_handoff_context_pack`

Each context pack should answer:

- what should the receiving agent know right now?
- what are the critical facts?
- what changed recently?
- what actions or decisions are pending?
- what contradictions or uncertainties should the agent keep in view?

Context packs should be explicitly optimized for:

- compactness
- direct reuse by agents
- regeneration on demand

### 3. Contradiction Objects

Contradictions should not merely be buried in prose.

Introduce a clearer contradiction model that can represent:

- conflicting claims
- scope of conflict
- severity
- freshness
- unresolved vs resolved state
- optional suggested resolution path

This is especially important for preserving useful tension rather than
prematurely smoothing everything into one narrative.

### 4. Decision / Change Views

HAETSAL should treat decisions and recent change as first-class compiled
artifacts.

At minimum, refine support for:

- `decision_log`
- `what_changed`

These do not need a complete product surface yet, but the compiled schema should
know how to represent them clearly.

## Required Schema/Model Refinements

This session should refine the compiled families into clearer read/write shapes.

### Dossier Semantics

Add or refine fields that distinguish:

- stable identity
- subject type
- summary
- key facts
- key relationships
- recent updates
- open questions / unknowns
- contradictions
- recommended next reading / next actions

This can be implemented via:

- explicit columns where appropriate
- structured JSON sections where variation is useful

The choice should be made carefully and documented in As-Built.

### Context Pack Semantics

Context packs should have a consistent internal shape.

At minimum they should support sections like:

- `situation`
- `critical_facts`
- `recent_changes`
- `decisions`
- `contradictions`
- `recommended_actions`
- `source_refs`

The exact field names may vary, but the model should become explicit rather than
implicit.

### Audience / Consumer Orientation

Compiled outputs should make audience explicit.

Examples:

- `human_readable`
- `agent_reusable`
- `chief_of_staff`
- `specialist_agent`

This should guide future compilation behavior and read-path selection.

### Regeneration / Version Semantics

The schema should preserve:

- stable identity across regenerations
- current version vs prior versions
- timestamps for compilation
- ability to re-render artifacts without changing conceptual identity

## Read Model Expectations

This session should define the first strong read model for compiled outputs.

That may include:

- typed dossier view structures
- typed context-pack view structures
- contradiction summary views
- helper readers for fetching the latest compiled object by family + stable key

These are internal read-model improvements, not yet a broad public product
surface.

## R2 Artifact Expectations

The schema refinement should also clarify how artifacts map to these models.

At minimum:

- dossiers should have a clear markdown/json artifact story
- context packs should have a clear json artifact story
- contradiction/change views should support compact renderable outputs

This session does not need to render every artifact flavor, but it should make
the intended mapping explicit.

## Product-Surface Expectations

Keep the product-surface additions minimal.

Allowed:

- tiny internal read helpers
- tiny debug/readback helpers if needed for verification

Avoid:

- broad new MCP tool expansion
- premature Chief of Staff cutover
- full user-facing dossier browser in this session

## Verification

Add or tighten tests for:

- dossier record creation with refined section semantics
- context-pack record creation with explicit agent-usable sections
- contradiction object storage and retrieval
- decision/change view storage semantics
- stable regeneration-safe identity across refined compiled families
- correct linkage from refined compiled objects to source truth and R2 artifacts

Run at minimum:

- dedicated `11.1` tests
- relevant compiled-synthesis foundation tests
- relevant canonical/Postgres tests
- `npm test`
- `npm run postflight`
- `npm run manifest`

## Deliverable

At the end of this session, HAETSAL should have:

1. a much sharper compiled object model
2. explicit dossier and context-pack semantics
3. a clear contradiction/change representation
4. internal read models ready for the compiler to target
5. a clean handoff to:
   - `11.2` compilation pipeline
   - `11.3` Chief of Staff compiled read path
