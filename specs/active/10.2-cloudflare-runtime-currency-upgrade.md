## What We're Building

Bring HAETSAL's Cloudflare runtime/tooling baseline current without changing
memory behavior.

This is the controlled platform-currency step before Hyperdrive, AI Search,
Agents Sessions, Hindsight removal, or retrieval-broker work.

This session should:

- update Cloudflare-facing package ranges
- update the Worker compatibility date
- keep `nodejs_compat`
- verify Wrangler config shape against the current local schema
- generate or validate Cloudflare binding types
- document what changed and what remains deferred

This session should not add new product bindings yet.

---

## Why This Session Exists

The 10.0 and 10.1 work established that the 11.4 lineage is the right runtime
baseline. The next risk is that HAETSAL is still running on older Cloudflare
tooling assumptions:

- compatibility date is `2025-01-01`
- `agents` package is declared at `^0.7.5`
- `wrangler` is declared at `^4.83.0`
- `@cloudflare/workers-types` is declared at `^4.20250303.0`
- `@cloudflare/vitest-pool-workers` is declared at `^0.14.7`
- AI Search, Hyperdrive, and newer Agents memory/session capabilities should be
  evaluated from a current toolchain, not from stale types

Cloudflare's current Workers guidance says to keep compatibility dates current,
use `nodejs_compat`, and generate binding types from Wrangler configuration.
This session brings the foundation up to that standard while leaving product
architecture decisions to later specs.

## Implementation Steps

### 1. Update Package Ranges

Update `package.json` Cloudflare-facing package ranges to current npm latest.

Expected package changes if executing on 2026-06-01:

```json
{
  "dependencies": {
    "@cloudflare/containers": "^0.3.5",
    "@cloudflare/puppeteer": "^1.1.0",
    "agents": "^0.13.3"
  },
  "devDependencies": {
    "@cloudflare/vitest-pool-workers": "^0.16.10",
    "@cloudflare/workers-types": "^4.20260601.1",
    "wrangler": "^4.95.0"
  }
}
```

Do not upgrade non-Cloudflare packages unless a Cloudflare package peer
dependency requires it. If npm rewrites local ignored lockfiles within existing
ranges, record it but do not force-add ignored lockfiles.

Important repository policy:

- `package-lock.json` is currently not tracked in this tree.
- `.gitignore` ignores `package-lock.json`.
- Do not change that policy in this spec.

### 2. Refresh Local Dependencies

Run a normal install only after `package.json` is edited:

```powershell
npm install
```

If `npm install` changes only ignored lockfiles and `node_modules`, that is
acceptable. Do not force-add them.

### 3. Update Compatibility Date

Update `wrangler.toml`:

```toml
compatibility_date = "2026-06-01"
compatibility_flags = ["nodejs_compat"]
```

If executing on a later date, use the execution date instead of `2026-06-01`
and record the exact date in the report.

Do not reformat unrelated `wrangler.toml` comments or bindings.

### 4. Validate Wrangler Config

Run:

```powershell
npx wrangler deploy --dry-run
```

If the dry run requires credentials, tries to build unavailable containers, or
touches live resources, stop that command and use:

```powershell
npx wrangler types --help
```

plus the test/postflight suite as the local validation signal. Record why
`deploy --dry-run` was not usable.

### 5. Generate Binding Types

Cloudflare docs recommend generated binding types from Wrangler config. Add a
script if one does not exist:

```json
{
  "scripts": {
    "cf:types": "wrangler types src/types/cloudflare-env.generated.d.ts --include-runtime false"
  }
}
```

Then run:

```powershell
npm run cf:types
```

If the generated file creates type conflicts, do not force a large Env refactor
in this session. Instead:

1. keep or remove the generated file based on whether tests pass
2. document the delta between generated bindings and `src/types/env.ts`
3. defer adoption of generated Env as a separate spec

Preferred outcome:

- `src/types/cloudflare-env.generated.d.ts` exists
- tests pass
- manual `src/types/env.ts` remains unchanged

## Cloudflare Product Decisions For This Session

### Hyperdrive

Relevant, but not implemented in 10.2.

Hyperdrive should be the likely Cloudflare-side connector for Neon/Postgres in
the next data-plane spec. Current docs position it for existing Postgres/MySQL
databases from Workers and require `nodejs_compat` for common database drivers.

Do not add the binding in this spec because adding it changes runtime env shape
and should be paired with canonical Postgres connection code.

Expected next data-plane spec:

- `10.3-hyperdrive-neon-canonical-connection.md`

### AI Search

Relevant, but not implemented in 10.2.

AI Search now has Workers bindings, built-in storage for new instances, hybrid
search, metadata filtering, MCP endpoints, and cross-instance patterns. It is a
candidate projection/index for compiled docs and source search.

Do not add an AI Search binding here because the retrieval broker and compiled
document indexing strategy should decide instance boundaries and freshness.

Expected later retrieval spec:

- `10.5-ai-search-retrieval-projection.md`

### Agents Sessions / Think

Relevant, but not implemented in 10.2.

Agents SDK has newer session/context and Think-related capabilities that matter
for agent context management. This session only gets the package baseline current
so those APIs can be evaluated from current types/docs.

Expected later context spec:

- `10.6-agent-session-context-and-think-evaluation.md`

### Containers / Sandboxes / Workers Mesh

Not adopted in 10.2.

Containers remain only because existing Hindsight and Graphiti runtime paths
still reference them. This spec must not add new container uses. Sandboxes and
Workers Mesh remain future evaluations tied to concrete needs.
