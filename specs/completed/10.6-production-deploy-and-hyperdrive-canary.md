## Brain Laws Check

### Law 1: One Public Face

No new public brain surface is planned. The deploy uses the existing Worker
entry point and existing routes.

### Law 2: Zero-Knowledge

No memory content should be read or written by the deployment itself. The
production canary must only prove the Worker has the Hyperdrive binding and
must not write memory, mutate user data, or print any database connection
string.

### Law 3: Agent Write Policy

No change to source authority, write policy, salience, review, or capture
rules.

### Law 4: Post-Hindsight Direction

No Hindsight removal in this spec. Hindsight keeps its existing container and
`NEON_CONNECTION_STRING` path.

### Law 5: Canonical Cloudflare Data Path

HAETSAL-owned canonical Postgres access should use `HYPERDRIVE_CANONICAL` in
production. Direct canonical connection strings remain local/fallback only.

Discovered Constraints:

- The public hostnames are protected by Cloudflare Access before Worker code
  runs. Unauthenticated `HEAD /_canary/hyperdrive` requests were redirected or
  rejected before reaching the Worker.
- The production canary therefore requires an existing CF Access service token.
- PowerShell in this environment does not support
  `Invoke-WebRequest -SkipHttpErrorCheck`; the canary used `HttpClient`.
- The rolled Cloudflare API token was used process-locally only and was not
  written to repository files.
