## What We're Building

Turn the broker trace foundation from Session 9.8 into a real **tenant-visible
memory trace product**.

Session 9.8 already shipped:

- broker default read path
- primary + shadow retrieval
- D1 index rows in `canonical_broker_traces`
- tenant-encrypted rich detail blobs in `R2_OBSERVABILITY`

What does **not** yet exist is a proper tenant-facing way to inspect that data.

Session 9.9 adds:

- a canonical tool/service to list recent traces for the tenant
- a canonical tool/service to fetch one full trace
- a stable tenant-facing contract for what a trace is
- a clear separation between:
  - tenant full-fidelity visibility
  - platform-owner blindness to raw tenant traces

This is a tenant product, not a platform analytics system.

---

## Why This Session Exists

The broker now compares engines in the background, but without readback the
system is only learning implicitly.

For HAETSAL-as-a-personal-open-brain, the tenant should be able to inspect:

- what they asked
- what HAETSAL chose as the primary route
- what the shadow engine found
- what was shown to them
- where the answer came from

That visibility matters for:

- trust
- debugging
- understanding the broker
- later route/synthesis tuning

This is especially important before platform-wide learning or canonical
Postgres migration, because it gives the tenant immediate value from the
brokered architecture.

## Strategic Scope

### In Scope

- tenant-facing trace readback
- recent-trace listing
- full-trace retrieval
- hydration of encrypted detail blobs for the authenticated tenant
- trace access control
- broker trace visibility for both `search_memory` and internal context-builder
  brokered queries

### Explicitly Out of Scope

- platform-owner/global analytics view
- anonymized cross-tenant learning system
- broker synthesis
- canonical Postgres migration
- broad UI product beyond the canonical tool/service surface

## THE Brain Laws Check

### Law 1: One Public Face

Trace readback must live behind the existing McpAgent/Worker canonical surface.
This session must not expose raw storage or R2 directly.

### Law 2: Zero-Knowledge

Tenant traces may be rich for the tenant, but no raw tenant trace should become
visible through D1/KV/Analytics or through a broad operator surface. Rich trace
detail must continue to respect the tenant-encrypted archive model.

### Law 3: Agent Write Policy

This is a read-side introspection session only. It must not widen memory or
action write authority.

## Behavioral Wiring

### Authorization

| Route / Entry Point | Auth Level | Tenant ID Source | When Checked |
|---------------------|-----------|-----------------|-------------|
| `get_recent_memory_traces` via McpAgent | Existing auth/session path | Existing tenant context | Existing auth middleware + DO bootstrap |
| `get_memory_trace` via McpAgent | Existing auth/session path | Existing tenant context | Existing auth middleware + DO bootstrap |
| Internal trace readback service | Trusted internal caller | Service arg / tenant context | At service boundary |

No intentionally public HTTP route is added in this session.

### Action Layer

No action tools in this session.

### Audit / Trace

Trace readback should follow existing metadata-only read telemetry patterns if
they already exist, but this session must not create a second noisy audit
stream for every trace view.

### Compute Routing

| Operation | Tier | Rationale |
|-----------|------|-----------|
| List recent trace summaries | Sync Worker / service | Interactive read |
| Fetch full trace detail | Sync Worker / service | Interactive read |
| Decrypt rich detail blob | Sync Worker / service using authenticated tenant context | Needed for tenant-facing detail |

### Other Behavioral Wiring

- Trace detail readback must be scoped to the authenticated tenant only.
- If a rich detail blob is unavailable or undecryptable, the structured D1
  summary should still be returned truthfully with an explicit gap.
- The public trace contract should remain engine-aware enough to be useful, but
  not leak irrelevant internal implementation noise.

## Part 3: Types / Contract

The tenant-facing contract should define shapes along these lines:

```typescript
export interface CanonicalBrokerTraceListItem {
  queryId: string
  createdAt: number
  requestedMode: MemoryQueryModePreference | null
  primaryMode: MemoryQueryMode
  shadowMode: MemoryQueryMode | null
  primaryStatus: CanonicalBrokerBranchStatus
  shadowStatus: CanonicalBrokerBranchStatus
  overlap: CanonicalBrokerOverlap
  surfacedSummary: string | null
}

export interface CanonicalBrokerTraceView {
  queryId: string
  createdAt: number
  queryText: string | null
  requestedMode: MemoryQueryModePreference | null
  route: CanonicalMemoryRouteDecision
  primary: CanonicalBrokerBranchTrace
  shadow: CanonicalBrokerBranchTrace
  surfaced: {
    mode: MemoryQueryMode
    status: string
    summary: string | null
    itemCount: number
  }
  overlap: CanonicalBrokerOverlap
  detailStatus: 'ok' | 'missing' | 'undecryptable'
}
```

The public contract must answer:

- what happened?
- what was shown?
- what did the shadow engine do?
- what can the tenant inspect later?
